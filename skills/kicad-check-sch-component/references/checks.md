# 符号校验：每一项检查的数据来源与判定

符号的错分两类，**必须分开查**，因为抓它们的通路完全不重叠：

| 类 | 例子 | 谁抓得到 | 谁抓不到 |
|---|---|---|---|
| **A 和手册对不上** | 引脚 9/10 名字写反、ALERT 写成 output、少了某个引脚 | 网表 + ERC + PDF 比对 | 规矩检查（它不知道手册） |
| **B 和 house style 对不上** | 引脚间距 100 mil、两组之间只隔 200 mil、引脚没落在栅格上 | 规矩检查 | 网表/ERC（它们不看位置） |
| **C 都要人看** | 分组观感、名字压字、Pin1 朝向、本体比例失调 | 渲染 + 目视 | 以上全部 |

---

## 通路 A —— 规矩检查（`symbol_lint.py`）

纯几何，读 `.kicad_sym` 的文本，不需要 KiCad，跑得很快。

| kind | 查什么 | 判定 | 为什么必须查 |
|---|---|---|---|
| `duplicate` | 引脚号重复 | 任何重复 → FAIL | KiCad 会静默取其一，网表看起来还是对的 |
| `off_grid` | 引脚端点是否落在连接栅格（默认 50 mil） | 不在 → FAIL | 会导致**连不上线**，但画出来完全正常 |
| `pin_length` | 引脚长度是否一致 | 不一致 → warn | 观感问题 |
| `pitch` | 组内间距 | < `--min-pitch`（默认 200 mil）→ FAIL | 手册不规定，只能查规范 |
| `group_gap` | 组间间距 | < `--group-gap`（默认 400 mil）→ FAIL | 同上 |
| `multiple` | 间距是否是基础间距的整数倍 | 不是 → FAIL | 抓"半格错位"这种手滑 |
| `body_margin` | 引脚根部是否接在本体上 | 根部落在本体外 → FAIL | 引脚太短、悬空 |
| `overflow` | 左右两侧引脚名会不会挤在一起 | 估算需要宽度 > 本体 → warn | **估算值**，以渲染图为准 |
| `no_power` | 有没有 `power_in` 引脚 | 没有 → warn | 电源脚漏画 |
| `fields` | 位号/Value 是否落在本体内 | 落在内 → warn | 观感 |

### 致命限制：分组是**输入**，不是推断出来的

> **「组间 400 mil」这条规则几何上不可判。**

实测证据（`symbol_lint.py` 的负向测试）：左侧原本是

```
VBUS(12.7)  ──400mil──  IN+(2.54)  ──200mil──  IN-(-2.54)
```

把 `IN+` 从 2.54 提到 7.62，几何上就变成

```
VBUS(12.7)  ──200mil──  IN+(7.62)  ──400mil──  IN-(-2.54)
```

两组间距分别是 200 和 400 —— **依然满足"组内 200 / 组间 400"**，只是分组变成了
`{VBUS, IN+} | {IN-}`。光看坐标，工具无法区分"符合规范的另一个分组"和"你搭错了"。

所以：

* 必须用 `--groups groups.json` 把**语义分组**告诉工具（见
  `assets/groups_template.json`）；
* 不给分组时，工具只能几何推断，并且会明确打印
  `[!] 未提供 --groups：分组只能几何推断，「组间 400 mil」这条规则无法真正校验`；
* 给了分组之后，工具做三件事：
  1. 组内间距是否都等于基础间距且 ≥ min-pitch
  2. 相邻组之间是否 ≥ group-gap
  3. **几何推断出的分组 vs 声明的分组**是否一致 —— 不一致直接 FAIL

第 3 条是关键：它把"我以为的分组"和"画出来的分组"对上了。

## 通路 B —— 网表（`sch_netlist.py`）

```
我写 .kicad_sym  ->  sch_build 建最小原理图  ->  kicad-cli 导网表  ->  读 libparts 的 pin
```

拿到的 `(num "1") (name "~{CS}")` 是 **Eeschema 解析那个符号之后给出的**，
不是读我自己的文本。所以能抓到"文本看着对、KiCad 读出来不对"的错：

* 引脚写在了子单元（`SYM_1_1`）外面，父块里没有 → 网表里就少引脚
* 符号块结构被截断（`embedded_fonts`、多余括号）
* `number` 重了 → 网表里只剩一个

顺带还能拿到 `Footprint` / `Datasheet` / `Description` 字段，用来核对链接。

`sch_build.py` 里有个坑值得记住：**放置点必须落在连接栅格上**。
一开始放在 `100, 100`（100 / 1.27 = 78.74，不在栅格上），ERC 对每个引脚报
`endpoint_off_grid` —— 那是尺子的问题，不是符号的问题。现在会自动吸附到 1.27 mm。

## 通路 C —— ERC（`sch_erc.py`）

**关键认识：孤立放一个符号跑 ERC，必然报一堆 `pin_not_connected` /
`pin_not_driven`。那是"符号没接线"的必然结果，不是符号的缺陷，判为 expected。**

真正有价值的是报告里这种行：

```
@(89.84 mm, 87.30 mm): Symbol U1 Pin 8 [VBUS, Input, Line]
                                              ^^^^^  ^^^^^
```

方括号里的 `NAME, TYPE, STYLE` 是 **Eeschema 认定的电气类型**。
拿它和手册 TYPE 列比，就独立验证了"电气类型有没有写错"。

**为什么这条不能用别的方式代替**：电气类型画出来完全一样，尺寸也全对 ——
`MISO` 标成 `input` 还是 `output`，渲染图、Gerber、间距检查都看不出来。
只有 ERC 会说。

`sch_erc.py` 里 `EXPECTED` 集合列出的是孤立符号必然项，其余才需要人看。
其中 `endpoint_off_grid` **不在** expected 里 —— 它是真信号（引脚坐标没落栅格）。

### 还没做但值得做的

现在的 ERC 只跑"孤立符号"。更强的做法是搭一个**测试台**（testbench）原理图：
VS/GND 接电源符号、输入接驱动、输出接负载、ALERT 接上拉，
这样 ERC 能真正判"输出冲突""电源没驱动"这类跨引脚的电气错误。

现阶段靠"孤立符号 ERC + 类型提取"覆盖了主要风险；测试台是下一步。

## 通路 E —— 引脚↔焊盘契约（`pinmap.py`）

唯一真正的跨 artifact 耦合点。**这个检查天然是联合的**，不属于任何一侧：

* 符号侧能查的：每个 pin number 在封装里有没有对应 pad
* 封装侧能查的：每个 pad number 在符号里有没有对应 pin

两个 skill 都能跑 `pinmap.py`，但结论只有在两边数据都在手时才成立。
所以报告里的措辞要写清楚：`符号 10 引脚 vs 封装 10 焊盘，一一对应`
—— 而不是"本侧检查通过"。

## 判定的措辞（重要）

| 措辞 | 什么时候能写 |
|---|---|
| `规矩 PASS（间距/分组/栅格/本体 均无 FAIL）` | `symbol_lint` 跑过 |
| `手册比对 PASS：10/10 引脚号、名、电气类型一致` | PDF 与网表/ERC 三方比对过 |
| `ERC PASS（已扣掉孤立符号必然的 20 项）` | ERC 跑过 |
| `目视确认：分组清楚、无压字、电源脚朝上` | **真的看过图之后** |
| `待目视` | 图出了但没看 —— 不许写成"已验证" |
| `未做：测试台 ERC` | 一直要写，直到真的做了 |

一条完整结论长得像这样：

> 符号 `INA239`：规矩检查 0 FAIL（左侧 `{VBUS} | {IN+, IN−}` 间距 400/200 mil，
> 右侧 `{MOSI,MISO,SCLK,CS} | {ALERT}` 间距 200/200/200/400 mil）；
> 网表 10 引脚，与手册 Table 5-1 的号/名/电气类型 10/10 一致；
> 孤立符号 ERC 除必然项外 0 违规；引脚↔焊盘契约与封装一一对应；
> 渲染图已目视：分组清楚、CS/ALERT 上划线正确、无压字。
> **未做**：测试台 ERC（跨引脚电气冲突）、实物验证。

最后那句"未做"不能省。
